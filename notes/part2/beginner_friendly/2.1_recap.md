## 3) Networking fundamentals (VPC, subnet, route table, IGW, NAT)

### VPC and subnets

- VPC is your isolated IP network in AWS.
- A subnet is a slice of that VPC CIDR range.
- Public subnet has a route to IGW.
- Private subnet has no direct route to IGW.
- Subnets are AZ-specific, so you spread them across multiple AZs for resilience.
- CIDR planning matters early to avoid overlap and painful future migrations.

### Route tables

- Route tables decide where packets go next.
- Typical default routes:
  - Public subnet: `0.0.0.0/0 -> IGW`
  - Private subnet: `0.0.0.0/0 -> NAT Gateway`

What this means:

- `0.0.0.0/0` means "any destination not inside your VPC" (the default catch-all route).
- `-> IGW` means public-subnet resources can go directly to the internet.
- `-> NAT Gateway` means private-subnet resources go out through NAT for outbound internet access.

### IGW and NAT

- IGW enables internet connectivity for resources that route through it.
- NAT Gateway lets private instances initiate outbound internet traffic.
- NAT does not allow random internet-initiated inbound sessions to private instances.
- Cost-optimized workshop setup used one NAT, but production usually runs one NAT per AZ for HA and to reduce cross-AZ data transfer.

### Quick port primer

An IP address tells traffic which machine to reach.
A port tells traffic which service on that machine should receive it.

- Port 443 = HTTPS (encrypted web traffic)
- Port 80 = HTTP (unencrypted web traffic)
- Ephemeral ports (typically `1024-65535`) are temporary ports used by clients for return traffic

### What is NACL Rule 110 in this workshop?

Rule numbers in NACL decide evaluation order (lowest number first).
In your setup, Rule 110 is the "allow HTTPS" rule:

- Public NACL inbound Rule 110: allow TCP 443 from `0.0.0.0/0` (internet to ALB)
- Public NACL outbound Rule 110: allow TCP 443 to `0.0.0.0/0` (NAT/ALB outbound HTTPS)
- Private NACL inbound Rule 110: allow TCP 443 from `10.0.0.0/16` (VPC-internal app path)
- Private NACL outbound Rule 110: allow TCP 443 to `0.0.0.0/0` (app outbound HTTPS)

So when you hear "Rule 110," think: HTTPS traffic on port 443 is allowed for that direction.

Why this matters for you:
The request may go to 443, but the response often comes back to an ephemeral port.

## 4) Packet Flow #1 (User -> ALB -> EC2)

### Request path

1. A user browser starts an HTTPS request to your ALB on TCP 443.
2. Packet enters VPC via IGW.
3. Packet crosses into public subnet.
4. public NACL inbound allows 443 from `0.0.0.0/0` (rule 110).
5. ALB receives request and chooses a healthy target.
6. ALB forwards request toward EC2 in private subnet.
7. private NACL inbound allows 443 from VPC CIDR `10.0.0.0/16` (rule 110).
8. Your EC2 app receives and processes the request.

### Response path

1. Your EC2 sends a response using an ephemeral source port.
2. private NACL outbound allows ephemeral range to `10.0.0.0/16` (rule 120).
3. ALB receives response and forwards it to the client.
4. public NACL outbound allows ephemeral range to `0.0.0.0/0` (rule 120).
5. Response exits through IGW and reaches user browser.

Important note:
NACL is stateless, so return traffic must be explicitly allowed.

---

## 5) Packet Flow #2 (EC2 -> NAT -> Internet)

### Outbound path

1. Your EC2 in the private subnet sends an HTTPS request to an internet repo on 443.
2. private NACL outbound allows 443 to `0.0.0.0/0` (rule 110).
3. Private route table sends packet to NAT Gateway.
4. NAT performs source translation from private IP to NAT public IP.
5. public NACL outbound allows 443 to `0.0.0.0/0` (rule 110).
6. Packet exits through IGW to internet.

### Return path

1. Repo replies to NAT public IP on ephemeral destination port.
2. public NACL inbound allows ephemeral range from `0.0.0.0/0` (rule 120).
3. NAT reverses translation back to EC2 private IP.
4. private NACL inbound allows ephemeral range from `0.0.0.0/0` (rule 120).
5. Your EC2 receives the response.

Important note:
For NAT return traffic, source can still be internet-originated at NACL level. That is why `0.0.0.0/0` is expected in this rule.

## 6) NACL vs Security Group

NACL:

- Subnet-level control
- Stateless
- Ordered rules
- Supports allow and deny
- Needs explicit ephemeral return-path rules

Security Group:

- Resource-level control (ENI level)
- Stateful
- Allow rules only
- Return traffic is automatically allowed for established sessions

Simple rule of thumb:
Use Security Groups for resource-to-resource intent.
Use NACLs for subnet boundary guardrails.

In this workshop specifically:

- ALB SG allowed inbound 80/443 from internet and outbound to app SG
- App SG allowed inbound 80/443 only from ALB SG and outbound HTTPS for egress

Prompt:
Where should RDS be placed and what must change?

Your answer should include:

- Place RDS in private subnets

### Exercise B: NAT failure scenario

Prompt:
If NAT Gateway is down, what breaks first?

Your answer should include:

- Private EC2 cannot fetch packages or call internet APIs
- Existing inbound user flow through ALB may still work if app does not depend on internet calls
- Logs and updates that require internet egress fail

### Exercise C: VPC endpoint decision

Prompt:
When should we use VPC endpoints?

Your answer should include:

- Use interface endpoints for services like SSM
- Use gateway endpoint for S3
- Benefits: private path, less internet dependency, clearer security controls

Extra check:

- For SSM in private subnets, you needed interface endpoints for `ssm`, `ssmmessages`, and `ec2messages`.
- For S3 from private subnets, you used a gateway endpoint attached to private route tables.

## 8) IAM recap (Role -> Instance Profile -> Temporary Credentials)

- IAM Role defines permissions
- Instance Profile is how role is attached to EC2
- EC2 gets temporary credentials automatically from AWS
- Avoid storing long-lived static AWS keys on instances

Part 1 specifics:

- Custom app policy allowed S3 read access for your app content bucket
- Managed policy `AmazonSSMManagedInstanceCore` enabled SSM management without opening SSH
- Trust policy allowed the EC2 service to assume the role

Why this is better:

- Reduced credential leak risk
- Easier rotation and auditing
- Cleaner least-privilege implementation

## 9) EC2 recap (AMI, user data, debugging, cattle vs pets)

### Launch and bootstrap

- AMI defines base OS image
- User data runs startup automation (install packages, configure app, start service)
- User data fetched your web content from S3 and updated instance-specific values via IMDSv2

### Debugging checklist

- Check service state: `systemctl status`
- Test app locally: `curl localhost`
- Review startup logs: cloud-init and user data logs
- Verify role credentials and metadata via IMDSv2 when S3 pulls fail

### Operating mindset

Treat instances as replaceable (cattle, not pets).
If a node drifts badly, rebuild from known-good automation.

## 10) Terraform recap (code -> plan -> apply)

In Part 1, you used Terraform to define infrastructure as code instead of manually clicking through the console.

Basic workflow:

1. `terraform init` (prepare provider/plugins)
2. `terraform plan` (preview proposed changes)
3. `terraform apply` (execute approved changes)
4. `terraform destroy` (tear down when needed)

Key concepts:

- `resource` blocks describe desired infrastructure
- references connect resources together
- state tracks what already exists
- remote backend in S3 keeps state centralized
- DynamoDB lock prevents concurrent apply conflicts
- `terraform import` helps recover from accidental ClickOps by bringing existing resources back into code management

Example:

```hcl
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name = "vpc-main"
  }
}
```

### Optional answer guide (check only after you attempt)

1. ALB must be internet-reachable, while EC2 should remain non-public for stronger security.
2. Private subnet has no direct IGW route; NAT provides controlled outbound internet access.
3. NACL is stateless, so return traffic must match explicit allow rules (often ephemeral range).

5. Remote state makes collaboration consistent, and locking prevents two applies from corrupting state.
