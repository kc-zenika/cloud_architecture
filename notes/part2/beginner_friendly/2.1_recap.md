  # Part 1 Recap — For the Zero-Foundation Folks

> If you left Part 1 feeling abit lost, this is for you.  
> No assumed knowledge. We'll build the mental model first, then tie it to what we actually did.
This recap is designed to strengthen your understanding of the architecture from Part 1 before we move into Part 2.
The goal is to make the network story clear enough that you can explain the packet flow in your own words.

---

## 1) What we built

In Part 1, we deployed a small app on AWS with these building blocks:

- VPC (our private network)
- Public and private subnets
- Internet Gateway (IGW)
- NAT Gateway
- Route tables
- NACLs and Security Groups
- EC2 app server in private subnet
- ALB in public subnet
- IAM role + instance profile for EC2
- VPC endpoints (SSM and S3 related access)

Key idea:
Users can access the application through the ALB, while the EC2 instance itself remains private.

---

## 2) Core networking ideas

- Public subnet: has a route to IGW
- Private subnet: no direct route to IGW
- NAT Gateway: lets private instances go out to internet, but does not allow random inbound connections

One helpful way to picture this is:

- IGW is the main gate of the VPC
- NAT is the controlled exit for private workloads
- Route table decides which gate traffic can use

---

## 3) The two packet flows you must understand

Before we walk the flows, we need one important networking idea: ports.

### What is a port?

An IP address tells traffic which machine to go to.
A port tells traffic which service or application on that machine should receive it.

Think of it like this:

- IP address = the street address of a building
- port = the room number or department inside the building

If a packet reaches the right machine but the wrong port, it still will not reach the correct application.

### What is port 443?

Port 443 is the standard port for HTTPS.
HTTPS is secure web traffic, which means the data is encrypted while it travels across the network.

So when a browser opens a normal secure website, it usually talks to destination port 443.

Examples:

- `https://example.com` usually uses port 443
- `http://example.com` usually uses port 80

In our Part 1 setup, the user reaches the ALB on port 443 because the ALB is accepting secure web traffic.

### What are ephemeral ports?

Ephemeral ports are temporary high-numbered ports, usually in the range `1024-65535`.
They are commonly chosen automatically by the client side of a connection.

For example:

- your browser wants to visit a website
- it sends a request to destination port 443 on the server
- but your own browser also needs its own temporary port for the conversation
- AWS NACLs must allow the return traffic to that temporary port

That is why you often see:

- request goes to port 443
- response comes back to an ephemeral port

This is one of the biggest reasons learners get confused by NACL rules.
The request and response are part of the same conversation, but they are not always using the same port number on both sides.

Let us use the NACL slideshow as our guide. At each hop, ask two questions:

1. Where is this packet now?
2. Which gatekeeper is checking it right now?

Analogy to keep in mind:

- VPC = office compound
- IGW = front gate
- Public subnet = reception floor
- Private subnet = staff-only floor
- ALB = receptionist who routes visitors
- NAT = outbound mailroom for staff
- NACL = floor security desk (checks every packet, no memory)

### Flow 1: User -> App -> User

You can picture this flow as a visitor entering a building, checking in at reception, being routed to the correct staff member, and then receiving a reply.

Request path (towards app):

1. Browser opens HTTPS connection to ALB DNS on TCP 443.
2. Packet arrives at IGW (front gate of VPC).
3. Packet heads into public subnet boundary.
4. public NACL inbound checks packet:
	- source = internet IP
	- destination port = 443
	- rule 110 allows it (`0.0.0.0/0 -> 443`)
5. ALB receives packet.
6. ALB selects backend target and forwards to app in private subnet.
7. Packet hits private subnet boundary.
8. private NACL inbound checks packet:
	- source now appears from inside the VPC path (the ALB side)
	- destination port = 443
	- rule 110 allows it (`10.0.0.0/16 -> 443`)
9. App receives request and generates response.

Response path (back to user):

1. App sends response from an ephemeral source port (`1024-65535`).
2. Packet exits private subnet boundary.
3. private NACL outbound checks packet:
	- destination back toward ALB path in VPC
	- ephemeral port usage is expected for return leg
	- rule 120 allows (`to 10.0.0.0/16, 1024-65535`)
4. ALB receives app response.
5. ALB sends response back to internet client.
6. Packet exits public subnet boundary.
7. public NACL outbound checks packet:
	- destination = internet client
	- destination port is client-side ephemeral port
	- rule 120 allows (`to 0.0.0.0/0, 1024-65535`)
8. Packet leaves through IGW and reaches browser.

Common point of confusion:
The request goes to port 443, but the return traffic usually targets an ephemeral client port rather than 443. Because NACLs are stateless, that return path must be explicitly allowed.

### Flow 2: App -> Internet repo -> App (via NAT)

You can picture this flow as a staff member sending a package out through the mailroom, receiving a reply, and having that reply routed back internally.

Outbound path (towards repo):

1. App starts outbound HTTPS to repo on TCP 443.
2. Packet reaches private subnet boundary.
3. private NACL outbound checks packet:
	- destination = internet
	- destination port = 443
	- rule 110 allows (`0.0.0.0/0 -> 443`)
4. Route table sends packet to NAT Gateway (mailroom).
5. NAT performs source NAT:
	- source changes from private IP to NAT public IP
	- this allows the internet service to send the reply back to the NAT Gateway
6. Packet reaches public subnet boundary.
7. public NACL outbound checks packet:
	- destination = internet
	- destination port = 443
	- rule 110 allows
8. Packet exits via IGW and reaches repo.

Return path (back to app):

1. Repo replies to NAT public IP on ephemeral destination port.
2. Reply enters VPC via IGW and reaches public subnet boundary.
3. public NACL inbound checks packet:
	- source = internet repo IP
	- destination port = ephemeral
	- rule 120 allows (`0.0.0.0/0 -> 1024-65535`)
4. NAT receives reply and reverses translation:
	- destination remapped from NAT public IP back to app private IP
5. Packet moves toward private subnet boundary.
6. private NACL inbound checks packet:
	- source is still internet-originated at packet level
	- destination port = ephemeral
	- rule 120 allows (`0.0.0.0/0 -> 1024-65535`)
7. App receives response and connection completes.

Important note:
For NAT return traffic, `0.0.0.0/0` on ephemeral inbound rules is expected because the packet source is still an internet host, even though the NAT Gateway is in the path.

### Questions to ask while watching the slideshow

- Which subnet boundary is the packet crossing?
- Is this an inbound or outbound check?
- Is this the request port (443) or a return ephemeral port (`1024-65535`)?
- If a NACL rule is missing, at exactly which hop would traffic fail?

## 4) NACL vs Security Group

NACL:

- works at subnet boundary
- stateless (it does not remember the request)
- supports allow and deny
- needs explicit return-path rules (ephemeral ports)

Security Group:

- works at resource level (ALB/EC2 ENI)
- stateful (remembers request/response relationship)
- allow rules only
- return traffic is automatic once request is allowed

Why ephemeral ports matter:
If a NACL is stateless, you must allow `1024-65535` where required or the return traffic will be dropped.

## 5) IAM recap (why role + instance profile)

- We do not put long-lived AWS keys on EC2
- EC2 assumes an IAM role through instance profile
- AWS gives temporary credentials automatically
- This is safer and easier to rotate/audit

## 6) EC2 + app recap

- EC2 launched from AMI
- user data bootstraps dependencies and app setup
- app is reached through ALB, not direct public EC2 access

Useful checks from Part 1 debugging:

- check service state (`systemctl status`)

## 7) Terraform recap

In Part 1, we did not build the environment by clicking around manually in the AWS Console.
We described the infrastructure in Terraform.

That means:

- we write the desired infrastructure as code
- Terraform compares that code against reality
- Terraform tells us what it plans to create, change, or destroy
- Terraform can then apply those changes in AWS

Think of Terraform like a construction plan for your cloud environment:

- AWS is the land and building materials
- Terraform code is the blueprint
- `terraform plan` is the inspection of what needs to be built or changed
- `terraform apply` is the actual construction step

Some key Terraform ideas from Part 1:

- `resource` blocks describe things we want AWS to create
- arguments inside the block describe configuration details
- local names like `aws_vpc.main` let other resources refer to that resource
- Terraform state keeps track of what has already been created

Example:

```hcl
resource "aws_vpc" "main" {
	cidr_block           = "10.0.0.0/16"
	enable_dns_support   = true
	enable_dns_hostnames = true

	tags = {
		Name = "vpc-main"
	}
}
```

How to read this:

- `aws_vpc` means the resource type is a VPC from the AWS provider
- `main` is just the local Terraform name for that VPC
- `cidr_block` defines the IP range for the VPC
- the rest of the arguments define behavior and metadata

Common Terraform workflow:

1. `terraform init` to download the provider and prepare the working directory
2. `terraform plan` to preview changes
3. `terraform apply` to create or update infrastructure
4. `terraform destroy` to tear it down when needed

## 8) Quick self-check before Part 2

You are ready to move on if you can explain all of these clearly:


1. Why is the ALB in the public subnet while the app stays private?

The ALB must be reachable by users on the internet, so it needs to sit in a public subnet with a route to the IGW. The EC2 app stays in the private subnet so it is not directly exposed to the internet. This gives us a safer design: users talk to the ALB, and the ALB forwards only the allowed traffic to the app.

2. Why does the private subnet need NAT for outbound internet?

The private subnet has no direct route to the IGW, so the EC2 instance cannot talk to the internet on its own. The NAT Gateway gives the instance a controlled way to make outbound requests, such as downloading packages, without allowing unsolicited inbound internet traffic back to the instance.

3. Why does the NACL need explicit ephemeral rules?

NACLs are stateless, which means they do not remember that a request was previously allowed. Because of that, the return traffic must also match an allowed rule. Many return packets use ephemeral ports in the range `1024-65535`, so those ports must be explicitly allowed or the response will be dropped.
