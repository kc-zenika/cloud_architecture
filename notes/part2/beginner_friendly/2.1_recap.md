## 1. What Did We Actually Build?

We hosted a small web app called **DucksAsAService** (an nginx server serving an `index.html`) on AWS.

Here's the full picture:

![Architecture](architecture.png)

At the end of Part 1, we had:
- A **VPC** — our private, isolated network on AWS
- **Public + private subnets** across 3 availability zones
- An **Internet Gateway** — the door to the internet
- A **NAT Gateway** — lets private servers reach out, but not be reached
- **Route tables** — the signposts that direct traffic
- **NACLs + Security Groups** — two layers of firewall
- An **EC2 instance** running nginx, sitting in the private subnet
- **IAM roles** — so the EC2 could pull files from S3 without storing any passwords
- **VPC Endpoints** — so the admin (you) could connect to the EC2 via SSM without SSH

## 2. The Mental Model: Real-World Analogies

| AWS Thing | Analogy |
|---|---|
| **AWS Account** | Your company's account with a cloud provider — you own everything inside |
| **VPC** | Your private office building — the internet can't walk in uninvited |
| **Subnet** | A floor in the building. Public floor = reception (faces outside). Private floor = back office (no public access) |
| **Internet Gateway** | The front door of the building |
| **NAT Gateway** | A one-way revolving door for the back office — staff can go out, nobody can come in |
| **Route Table** | Signage inside the building — "to reach the internet, go to the front door" |
| **NACL** | A security checkpoint at each floor's entrance — checks everyone, doesn't remember faces |
| **Security Group** | The lock on each individual office door — remembers who it already let in |
| **EC2** | A physical computer (server) you're renting inside the building |
| **IAM Role** | An employee badge — defines what that computer is allowed to do |
| **S3** | A managed storage room outside the building, accessible via a key |

## 3. Why Did We Create Subnets in 3 Availability Zones?

An **Availability Zone (AZ)** is a physically separate data centre within the same AWS region. Singapore (`ap-southeast-1`) has three: `1a`, `1b`, `1c`.

Think of them as three separate buildings on the same campus. They share power grids and cooling only loosely — if one floods or loses power, the others keep running.

That's why we created **one public subnet and one private subnet per AZ** (6 subnets total):

```
ap-southeast-1a: public-1a  +  private-1a
ap-southeast-1b: public-1b  +  private-1b
ap-southeast-1c: public-1c  +  private-1c
```

If AWS has an incident in `1a`, traffic automatically reroutes to `1b` or `1c`. Your app stays up.

For Part 1 we only placed our EC2 in `private-1a` — but the network is already wired for high availability when we add a load balancer and more instances in Part 2.

> **Rule of thumb:** Always think in 3 AZs. The cost of the extra subnets is negligible. The cost of an outage is not.

## 4. Two Traffic Flows — Told as a Story

These are the two flows we designed the whole network around.

### Flow 1: A user opens the app in their browser

```
Internet User
    │
    ▼  (hits port 80/443)
Internet Gateway          ← the front door of the VPC
    │
    ▼
Application Load Balancer ← sits in the PUBLIC subnet, distributes traffic
    │
    │  [NACL check on public subnet — allows outbound to app]
    │  [Security Group check on ALB — only allows from the internet on 80/443]
    │
    ▼
EC2 (nginx)               ← sits in the PRIVATE subnet, serves the page
    │
    │  [NACL check on private subnet — allows inbound from VPC only]
    │  [Security Group check on EC2 — only allows from the ALB security group]
    │
    ▼
index.html is returned    ← the duck quacks 🦆
```

**Why is EC2 in the PRIVATE subnet?** Because we don't want random internet traffic hitting the server directly. The ALB is the only way in.

---

### Flow 2: EC2 pulls a package from the internet during boot (user data)

```
EC2 (private subnet)
    │
    ▼  (e.g. dnf install nginx)
NAT Gateway               ← sits in the PUBLIC subnet, masquerades as a public IP
    │
    ▼
Internet Gateway
    │
    ▼
Package Repos (internet)  ← downloads the package
    │
    ▼  (return traffic follows the same path back)
EC2 receives the response
```

**Why can't EC2 just go directly to the internet?** It's in a private subnet — there's no route to the IGW. NAT is the only path out, and it doesn't allow inbound connections.

## 5. Why Two Firewalls? (NACLs vs Security Groups)

This confuses almost everyone. Here's the key difference:

| | NACL | Security Group |
|---|---|---|
| **Where** | Subnet boundary (floor entrance) | Individual resource (office door) |
| **Stateful?** | ❌ No — must explicitly allow return traffic | ✅ Yes — return traffic is automatic |
| **Rules** | Allow + Deny | Allow only |
| **Use it for** | Broad perimeter rules (block entire IP ranges) | Fine-grained per-resource rules |

**Because NACLs are stateless**, we had to open ports `1024-65535` (ephemeral ports) — when your browser connects on port 80, the server's response comes back on a random high port that the client picked. The NACL has no memory of the original connection, so you have to explicitly allow those return ports.

**Security Groups don't have this problem** — they remember the connection, so return traffic is automatically allowed.

## 6. Why IAM? Why Not Just Store Credentials on the EC2?

The EC2 needed to pull `index.html` from S3. One way would be to paste an AWS access key onto the server — but this is dangerous:
- If someone gets into the server, they get your keys
- Keys don't expire automatically
- Hard to audit who used them

Instead, we used an **IAM Role + Instance Profile**:
1. We created a role (`DaaSAppRole`) that says "whoever wears this hat can read from S3"
2. We attached it to an **instance profile**, which is the mechanism that lets EC2 wear the hat
3. AWS automatically vends **temporary credentials** to the EC2 via the metadata service (`http://169.254.169.254`) — these rotate every few hours, no manual management

## 7. What is Terraform Doing?

Instead of clicking through the AWS Console to create all of the above, we wrote code (`.tf` files) that describes what we want. Terraform figures out how to create it.

```
terraform init    # Download the AWS "plugin" (provider)
terraform plan    # Preview: "here's what I'll create/change/delete"
terraform apply   # Actually do it
terraform destroy # Tear it all down
```

Here's the VPC we created, as Terraform code:

```hcl
resource "aws_vpc" "main" {       # resource type + your local name
  cidr_block           = "10.0.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name        = "vpc-main"
    Environment = "dev"
  }
}
```

- `resource` — you're telling Terraform to create something
- `"aws_vpc"` — the type of thing (comes from the AWS provider)
- `"main"` — just a nickname you give it inside your Terraform code, so other resources can refer to it (e.g. `aws_vpc.main.id`)
- Everything inside `{}` is the configuration — basically the form you'd fill in on the AWS Console, but as code

When you ran `terraform plan`, Terraform compared this code against its **state file** and said: "nothing exists yet — I'll create a VPC." When you ran `terraform apply`, it called the AWS API and created it.

**Why store state in S3?** The state file is Terraform's source of truth. If it only lives on your laptop and a teammate runs `terraform apply` from their machine, they won't know what already exists and will try to create duplicates. Storing state in S3 with a DynamoDB lock ensures only one person can run `apply` at a time, and everyone works from the same picture.
