
# System design
```
Design a planet-scale image-serving system that users can use to upload, search for, and view images
```
- inspired from https://sre.google/classroom/imageserver/
## End User requirements
1. Quickly and reliably access uploaded photos
2. Search images by keyword.
3. To share photos with friends and family

## Local (1-10 users)
- We start with a simple monolith — a single server that handles everything.
  - **Upload**: accepts photo uploads from the user.
  - **Download**: zips and serves photos back to the user.
  - **Search**: view photos, queries storage and metadata to find matching photos.
  - **Metadata**: stores and returns information about each image (e.g. filename, upload time, tags).
- everything reads/write from/to local disk
- request flow is straightforward: user → server → storage, all on one machine.

## Very small scale (100 users, 1 region)
- As storage grows, separate storage layer from the application server.
  - move photo storage to an external service
  - S3 object storage works well here, since metadata tells us which key maps to each photo.
  - metadata is still small enough to live on the same server.
- Comparison:
  - **EBS**: Network-attached block storage
    - block storage exposes raw disk space that your OS formats and manages, like plugging in a physical hard drive.
    - attached directly to your instance; only one instance can use it at a time*.
    - Bounded to a single AZ.
  - **EFS**: Network file system 
    - file storage organizes data into files and folders you can browse, like a shared network drive that multiple machines can mount.
    - multiple instances can read from it simultaneously.
    - bounded to a single region.
  - **S3**: Object storage that can be globally accessible.
    - each file is identified with a id
    - best fit for large files like photos.

## Small scale (10,000 users, 1 region)
- As traffic grows, we start hitting bottlenecks:
  - People search for photos far more often than they upload or download — reads far outnumber writes.
  - Users expect low latency for search, but uploads and downloads are more resource-intensive.
  - Uploads require long-lived network connections and consume significant RAM and bandwidth.
  - Downloads require CPU to compress data from storage before sending it to the client.
- Appropriate chance to break the monolith into four services: search, metadata, upload, and download.
  - We replicate the search and metadata services — **replicating for performance**.
  - Upload and download can still run as a single replica for now.
- 🚨 Problem: What happens when an AZ goes down?
  - We provision replicas in another AZ to absorb load if one AZ fails — **replicating for high availability**.
  - when one AZ fails, the load **Faileover** to the servers in the other AZ
  - AWS recommends: min 2x AZ, but best practice 3 (quorum based) 
  - in a way, this is also helping in performance, but mainly for HA
  - TODO diagram (same microservice, but now its deployed in sanother AZ)
- We add an ALB in front of the search and metadata services to distribute traffic.
- 🚨 Problem: Metadata relies on a local file, so we can't simply replicate it across servers.
  - ✅ Solution 1: Read from a central file store using EFS (network file system).
    - ⚖️ Trade-off: 
      - EFS reads are slower than local disk (~1–3ms vs ~0.1ms). 
      - There's no easy fix here without refactoring the metadata service to stop using files entirely.
      - TODO diagram (show the multiple metadata hits a EFS)
  - ✅ Solution 2: Shard the metadata — each server holds a subset of the records.
    - ie. cat photos go to metadata server A, dog photos to server B, etc.
    - Routing strategies include directory-based, hash-based, and consistent hashing.

    - ⚖️ Trade-off: 
      - Added operational complexity
      - adding a new metadata server requires rebalancing the data.

## Medium scale (50k-100k users, 2 regions)
- To reduce latency, we deploy services closer to our users using geolocation-based routing.
- ✅ S3 supports cross-region replication out of the box.
  - no issues for the storage layer
- 🚨 Problem: EFS is region-bound, so it can't serve our second region.
  - We migrate metadata to a multi-region database — DynamoDB global tables are a good fit here.
- **DynamoDB global tables** 
  - a fully managed, active-active setup NoSQL
  - each region holds a full copy of the data, and writes in any region are automatically replicated to all others
  - so reads and writes stay local to the user's region no matter where they are.
- Enable auto scaling to handle variable traffic:
  - scale up replicas when traffic increases
  - scale down when traffic is lower

## Large scale (1mil++ global users)
- At this scale, bottlenecks usually shift from infra/compute to data.
- metadata caching with key-value cache (`image_id` -> metadata)
  - keep frequently access records in fast cache
- storage caching with cloudfront
  - CloudFront distribution with S3 as the origin, which caches images
  - Edge caching (cached on Cloudfront nodes closest to your users), reducing latency globally. 
- Older, rarely accessed data 
  - by this time your app should have some older 
  - these doesn't need to live in the most expensive storage tier
  - S3 tiering keeps costs in check.

## Takeaways
- Replicating for performance vs. replicating for high availability (HA) 
  - they look the same but serve different goals.
- Sharding = partitioning data across multiple instances
  - it solves scale but adds routing complexity.
- Scaling compute is relatively straightforward; scaling data is where things get hard.
- Every design choice comes with trade-offs ⚖️:
  - A user in another region won't see an uploaded photo immediately — this is eventual consistency.
  - older data takes longer to load
  - We can shift upload/download to async flows using queuing to free up server resources.
  - Thumbnails don't need to be generated at upload time — lazy generation on first request is often good enough.
