
# System design
```
Design a planet-scale image-serving system that users can use to upload, search for, and view images
```
- inspired from https://sre.google/classroom/imageserver/
## End User requirements
1. Quickly and reliably access uploaded photos
2. Search images by keyword.
3. To share photos with friends and family

## Local (1-10 users)
- monolith with these features
  - upload
  - download
  - search (interacts with storage and metadata)
  - metadata (returns metadata of images)
- user -> server
- TODO diagram
## Very small scale (100 users, 1 region)
- when storage grows
  - move photo storage to an external
    - we can use s3 blob storage, since metadata will tell us which key to use 
  - metadata is small - lives on the same server
- block vs file vs blob storage
  - EBS: network attached block storage, AZ bounded
    - attached directly to your instance
  - EFS: network file system, region bounded
  - S3: object storage, can be global
- TODO diagram shows storage is external now
  - still 1 server
## Small scale (10,000 users, 1 region)
- bottlenecks!
  - people are searching for photos more often than upload/downloading (reads are way more than writes)
  - latency expectations of search is higher, but upload/download consumes more resources
  - Uploads require long lived network connections and uses RAM in the server and network bandwidth.
  - Downloads, uses some CPU to compress data from the storage system before sending it along to the client.
- separate out into services - search, metadata, download and upload services
  - replicate the search and metadata services
  - replicating for Performance
  - upload and download can still be in 1 replica
- problem! what happens when an AZ goes down?
  - provision replicas in another AZ, handle load if 1 AZ is down
  - replicating for High availability
  - TODO diagram
- problem! metadata relies on local file
  - we cant just replicate the metadata files
Solution 1:
  - read from a central file storage use a network file system (EFS)
  - Trade offs: reading from EFS is not the best for metadata
  - latency for network calls (~1–3ms vs ~0.1ms for local reads)
  - no other options unless we refactor our metadata service to not use files
Solution 2:
  - consider sharding
  - each metadata server contains a subset of files
  - ie. cat photos go to metadata server A, dogs to server B, etc
  - directory routing, hash-based, consistent hashing, etc
  - Trade offs: complexity, adding new metadata server needs to "rebalance"
- add a ALB infront of the search and metadata service
## Medium scale (50k-100k users, 2 regions)
- to reduce latency, we should deploy stuff closer to our users
  - geolocation based routing
- auto scaling
  - scale up replicas when traffic increases
  - scale down when its not needed too
- Can provision the servers in another region
- S3 we can do cross region replication 
- problem! - EFS is region bound
  - will need to shift the metadata to some sort of multi region database
  - use a DynamoDB global table

## Large scale (1mil++ global users)
- bottleneck usually shift from infra/compute to data
- metadata caching with key-value cache
  - keep frequently access ones in fast cache 
- storage caching with cloudfront
  - serve S3 data via cloudfront which caches images s
  - caching at the edge (closer to your users s)
- some data is old, not accessed
  - s3 tiering to keep cost lower


## Take aways
- replicating for performance vs replication for HA
- sharding - partitioning across multiple instances
- scaling compute is easy, data is difficult
- choose your trade offs
  - user in another region wont see the uploaded photos immediately (concept of eventual consistency) 
  - shift upload/download to async with queuing
  - lazy thumbnail generation
  - etc
