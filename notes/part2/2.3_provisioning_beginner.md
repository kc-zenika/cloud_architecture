- ClickOps is used to wire ASG and ALB resources while focusing on concepts and behavior.

## Full objective for this lab

In this lab, you are learning how compute scaling is managed with Auto Scaling Group (ASG).

Main idea:

- ASG is a continuous control loop.
- It compares actual state (running instance count and instance health) with desired state.
- If there is a gap, it reconciles by launching or terminating instances.

### ASG components you will use

- Launch template: defines what each instance should look like (AMI, instance type, role, user data).
- Min, max, desired capacity: desired is what ASG tries to maintain; min/max are safety boundaries.
- Scaling policy: adjusts desired capacity automatically based on a metric.
- Health checks: decide when an instance should be replaced.

### Scaling policy choices

- Target tracking: ASG keeps a metric near a target value (beginner default in this lab).
- Step scaling: scale by different amounts for different metric ranges.
- Scheduled scaling: scale based on known time patterns.
- Cooldown period: pauses additional scale actions for a short period after a scaling event, so ASG does not overreact and thrash.
- Warmup period: delays counting metrics from a newly launched instance until it has finished bootstrapping and stabilized.
- Connection draining (deregistration delay): when ASG removes an instance, ALB stops new requests to it but lets in-flight requests finish first.

### Self-healing behavior you will observe

- EC2 health checks verify instance/OS health.
- ELB health checks verify app health behind the target group.
- If an instance fails health checks, ASG replaces it automatically to restore desired capacity.

By the end, you should be able to explain not only how to click through setup, but why this architecture self-heals and scales under changing load.

## Prerequisites: Docker and access setup

### What Docker is (in this lab)

Docker lets you run tools in an isolated container instead of installing every tool locally.

In this lab, you will run Terraform inside Docker. This keeps setup consistent across different laptops.

### Check Docker installation

1. Check Docker CLI is installed.

```bash
docker --version
```

If you get command not found, install Docker first:

1. macOS option A (Docker Desktop direct download):
	- Install Docker Desktop from https://www.docker.com/products/docker-desktop/
	- Open Docker Desktop once after install and wait until it shows Docker Engine is running.

2. macOS option B (Homebrew):

```bash
brew install --cask docker-desktop
open -a Docker
```

Wait until Docker Desktop shows Docker Engine is running.

3. Windows:
	- Install Docker Desktop from https://www.docker.com/products/docker-desktop/
	- Open Docker Desktop and wait until Docker Engine is running.

4. Linux:

```bash
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
sudo usermod -aG docker $USER
```

After Linux install, log out and log back in so group changes apply.

5. Verify again:

```bash
docker --version
```

2. Check Docker engine is running.

```bash
docker ps
```

If `docker ps` fails, start Docker Desktop and retry.

## Prerequisites: Access setup

Before provisioning, set up your AWS access profile.

1. Log in via Zenika AWS Access portal.
2. Check whether your AWS config file already exists.

```bash
ls -la ~/.aws/config
```

If you see "No such file or directory", create it first:

```bash
mkdir -p ~/.aws
touch ~/.aws/config
```

3. Open your AWS config file with Vim.

```bash
vim ~/.aws/config
```

4. In Vim, press i to enter insert mode, then add this profile:

```bash
[profile sg-training-<Number>]
sso_start_url = https://d-80673a44b1.awsapps.com/start
sso_region = eu-west-3
sso_account_id = xxxxxxxxxx
sso_role_name = SandboxAccess
region = ap-southeast-1
```

5. Save and exit Vim.

Press Esc, then type `:wq` and press Enter.

6. Authenticate from CLI.

```bash
aws sso login --profile sg-training-X
export AWS_PROFILE=sg-training-X
```

7. Verify identity.

```bash
aws sts get-caller-identity
```

If this command fails, fix AWS authentication first before continuing.

## Update your account_id

The Terraform base files use your AWS account id in the backend and locals.

- If you use `./assets/tf_in_docker.sh bootstrap-base`, the script updates `aws/development/provider.tf` for you after login.
- If you are editing the files manually, replace `<ACCOUNT_ID>` with your actual AWS account id.

To get it:

```bash
aws sts get-caller-identity --query Account --output text
```

Make sure the value in `aws/development/provider.tf` matches your account before running the base setup flow.

Run the complete initial base setup flow (backend bucket + app asset upload + Terraform apply):

```bash
./assets/tf_in_docker.sh bootstrap-base
```


This beginner flow does not require local Terraform installation.

### Behind the scenes (what this command is doing)

You do not need to run these manually in beginner mode, but this is what happens under the hood:

1. Creates or validates Terraform backend bucket for state storage.
2. Builds the demo app binary and uploads it to S3.
3. Resolves your AWS account id and updates it in provider configuration.
4. Runs Terraform `init -reconfigure`.
5. Runs Terraform `plan` so you can see intended changes.
6. Runs Terraform `apply` to provision base resources.

This is the same workflow as the advanced path sections:

- Setup terraform backend again
- Push assets to S3
- Apply base resources

So beginner mode is not skipping the infrastructure work; it is automating the command sequence while you focus on architecture concepts.

For cleanup later:

```bash
./assets/tf_in_docker.sh base-destroy
```

After apply, verify these exist in AWS Console:

- VPC, subnets, route tables, NACLs
- IAM role and instance profile
- VPC endpoints
- App security group
- Launch template for app instances

## Part A: Create ASG in Console

### Step 1: Open Auto Scaling Group creation

1. Go to EC2 Console -> Auto Scaling Groups.
2. Click Create Auto Scaling group.

### Step 2: Choose launch template

Use these values:

- Auto Scaling group name: `part2-app-asg`
- Launch template: select the pre-created app launch template
- Version: `Latest`
- VPC: select your training VPC (vpc-main)
- Subnets: select private subnets only
- Availability Zone distribution: Balanced best effort
- Additional capacity settings: Default

Why private subnets:

- App instances should not be directly internet-facing
- Inbound traffic should come through ALB, not directly from the internet

### Step 3: Integrate with other services

- Load balancing: No load balancer
- VPC Lattice integration options: No VPC Lattice service
- Application Recovery Controller (ARC) zonal shift: Leave unchecked
- Health checks:
    - Health check type: `EC2` (leave ELB health checks off for now)
    - Health check grace period: `60`


### Step 4: Configure group size and scaling

Use these values:

- Group Size -> Desired capacity: `2`
- Scaling ->
    - Minimum capacity: `2`
    - Maximum capacity: `4`
    - Automatic scaling: Target tracking scaling policy
    - Scaling policy name: `part2-app-cpu-target-tracking`
    - Metric type: Average CPU utilization
    - Target value: `50`
    - Instance warmup : 300 (must type even if u see the 300)

Why `50`:

- Low enough to visibly trigger scale out during demo load
- High enough to avoid scale out under normal idle behavior

### Step 5: Instance maintenance policy
- Select: Launch before terminating
- Max healthy percentage: 110%

- skip Additional settings, keep deletion protection as default, placement group is none too

- skip notification

### Step 6: Add Name tag

Add tag:

- Key: `Name`
- Value: `part2-app-asg`


### Step 7: Create and verify

After creation:

1. Open EC2 Instances.
2. Filter by Name tag.
3. Confirm 2 instances are running in private subnets.

## Part B: Create ALB path in Console

You will now create the traffic path in this order:

1. ALB security group
2. ALB
3. Target group
4. Listener

Important port mapping for this lab:

- Client to ALB listener: `80`
- ALB to app instances (target group and security groups): `8080`

### Step 1: Create ALB security group

Go to EC2 -> Security Groups -> Create security group.

Use:

- Name: `part2-alb`
- Description : `Security group for part2 ALB`
- VPC: same VPC as app

Rules:

- Inbound: HTTP 80 from `0.0.0.0/0`
Type: HTTP
Protocol: TCP
Port range: 80
Source: Anywhere-IPv4 or 0.0.0.0/0
Description: Allow web traffic to ALB


- Outbound: Custom TCP 8080 to app security group
Type: Custom TCP
Protocol: TCP
Port range: 8080
Destination: the app security group
Description: Allow ALB to reach app instances

Decision checkpoint:

- If this is a private internal app, source should not be `0.0.0.0/0`.
- For this training lab, internet-facing access is intentional.

### Step 2: Confirm app security group allows ALB to app

In app security group:

- Ensure inbound TCP 8080 is allowed from ALB security group
- Ensure outbound HTTPS is allowed if app pulls from external services

If either rule is missing, add it now:

- Inbound rule:
Type: Custom TCP
Protocol: TCP
Port range: 8080
Source: `part2-alb` security group
Description: Allow ALB to reach app instances

- Outbound rule:
Type: HTTPS
Protocol: TCP
Port range: 443
Destination: `0.0.0.0/0`
Description: Allow app instances to reach package and AWS endpoints


### Step 3: Create ALB

Go to EC2 -> Load Balancers -> Create Load Balancer -> Application Load Balancer.

Use:

- Name: `part2-app-alb`
- Scheme: Internet-facing
- IP address type: IPv4
- VPC: training VPC (vpc-main)
- Subnets: public subnets of all of our az
- Security group: `part2-alb`


Listeners and routing look at step B4 => click create target group

### Step 4: Create target group

Use:

- Target type: Instances
- Name: `part2-app-tg`
- Protocol: HTTP
- Port: `8080`
- IP address type: IPv4
- VPC: vpc-main

Health check:

- Path: `/healthz`
- Protocol: HTTP
- Success code: `200`
- Interval: `30`
- Timeout: `5`
- Healthy threshold: `1`
- Unhealthy threshold: `2`

Decision checkpoint:

- Lower threshold catches failures faster but risks false alarms.
- Higher threshold is more stable but slower to react.


- skip registering targets!
### Step 5: Create listener and forward rule

In ALB listeners:

- Listener protocol: HTTP
- Listener port: `80`
- Default action: Forward to `part2-app-tg`

## Part C: Attach ASG to target group and switch health model

### Step C1: Attach ASG to target group

Go to EC2 -> Auto Scaling Groups -> `part2-app-asg`.
- Click Intergrations tag -> Loading balancing -> edit
- Select Application, Network or Gateway Load Balancer target groups 
- Add target group: `part2-app-tg`


Go to Target Groups -> part2-app-tg -> Targets.
You should see ASG instances register and move from initial to healthy.

If you see no targets at all, do these checks before moving to Step C2:

1. Re-open ASG -> Integrations -> Load balancing and confirm `part2-app-tg` is attached.
2. Confirm ASG has running instances in Instance management (desired 2, in-service 2).
3. Confirm target group type is Instances and VPC matches the ASG instances.
4. Confirm ALB SG outbound allows TCP 8080 to app SG.
5. Confirm app SG inbound allows TCP 8080 from ALB SG.
6. Wait 1-2 minutes and refresh the Targets tab.

Only continue to Step C2 after targets are registered and health checks are progressing.

If targets are registered but stay `unhealthy`, do this debug flow:

1. Start Session Manager on one ASG instance.
2. Run:

```bash
sudo systemctl status app --no-pager
curl -v http://localhost:8080/healthz
sudo tail -n 200 /var/log/cloud-init-output.log
```


### Step C2: Switch health check type

In ASG health settings:

- Change health check type from `EC2` to `ELB`

Why this is important:

- `EC2` detects infrastructure health (instance/OS)
- `ELB` detects application reachability (`/healthz`)
- With `ELB`, ASG can replace instances that are up but not serving traffic

## Fast troubleshooting checklist

If something does not work, check in this order:

1. Target group health check path is exactly `/healthz`
2. ALB listener forwards to correct target group
3. App security group allows inbound 8080 from ALB security group
4. ASG is attached to target group
5. ASG health check type is `ELB` after attachment
6. Instances are launched in private subnets in the expected VPC
