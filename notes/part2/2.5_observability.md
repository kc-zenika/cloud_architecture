
# What does it mean to be reliable?

Some engineering definitions for the training material:

**SLI (Service Level Indicator)** — a measurable signal of your app's health. e.g. "% of requests that complete in under 500ms"
**SLO (Service Level Objective)** — your internal target. e.g. "99% of requests should complete in under 500ms"
**SLA (Service Level Agreement)** — a contractual promise to customers. e.g. "We guarantee 99.9% uptime or you get a refund"

> SLOs live inside your team. SLAs face your customers. SLIs are the raw measurements that tell you whether you're meeting either.

**Monitoring** is the act of continuously collecting data about your system — metrics, logs, events — so you can spot problems and track reliability over time.

**Observability** is an approach to understanding health and performance of a system; how richly you can answer questions with that data. The difference becomes clear when something goes wrong:

> Your CPU alarm fires at 3am.
> - **Monitored but not observable**: you know CPU is high. That's all you know.
> - **Observable**: you open your logs, filter to that time window, see that `/slow` requests tripled, correlate it with a deploy at 2:45am, and find one EC2 instance handling all the traffic because health checks on the others started failing.
Same alarm. More data, richer tools = you can actually fix it.


See: https://sre.google/resources/practices-and-processes/measuring-reliability/

If your users feel its not reliable, then its not reliable.
Make a good guess to what makes your user feel its reliable.
Work backwards and try to monitor/observe it with telemetry data.

# The 3 pillars

All observability data falls into one of three categories:
> **LGTM** - logs, traces, metrics

| Pillar | What it is | AWS tool | Example |
|--------|-----------|----------|---------|
| **Logs** | Timestamped records of events | CloudWatch Logs | ALB access logs, app stderr |
| **Traces** | End-to-end path of a single request | AWS X-Ray | A request hitting ALB → microservice A → microservice B → DB |
| **Metrics** | Numeric measurements over time | CloudWatch Metrics | CPU utilization, request count |


In this session we focus on **metrics** and **logs** — the most actionable pillars for a beginner setup.

# What to measure — choosing the right metrics

With hundreds of metrics available, where do you start? Two frameworks give you a starting checklist.

## LETS — for your application (user's perspective)

| Signal | Question to ask | Our app |
|--------|-----------------|---------|
| **L**atency | How long do requests take? | `/slow` returns in 500ms–3s |
| **E**rror rate | How often do requests fail? | `/error` always returns 500 |
| **T**raffic | How much demand is the service under? | requests/second, transactions/second |
| **S**aturation | How "full" your service is. Knowing when it degrades. | % utilization |

> Google calls these the **Four Golden Signals**: https://sre.google/sre-book/monitoring-distributed-systems/

## How to pick a metric that matters

1. Start with LETS — this covers 90% of what you need
2. Ask: "If this metric is bad, would a user notice?" — if yes, it's worth tracking
  - Upload success rate
  - Image serve latency
  - cache hit ratio
3. Ask: "Can I act on this?" — metrics you can't respond to aren't worth alerting on
4. **Baseline first** — know what "normal" looks like before setting thresholds

# AWS Hands-on

## Part 1: EC2 Metrics & CloudWatch Dashboard

EC2 automatically sends metrics to CloudWatch every minute (basic monitoring). No setup required.

**Key EC2 metrics:**
- `CPUUtilization` — % of allocated CPU in use *(Utilization)*
- `StatusCheckFailed` — 1 if the instance or underlying host has failed *(Errors)*
- `NetworkIn` / `NetworkOut` — bytes transferred *(Utilization)*

**Console: Create a dashboard**
1. **CloudWatch** → **Dashboards** → **Create dashboard** → name it `observability-demo`
2. Add widget → **Line** → search `CPUUtilization` → select your EC2 instance(s)
3. Add another widget for `NetworkIn`
4. Save dashboard

> A dashboard gives you a single pane of glass — you're not hunting across EC2 instance pages one by one.

---

## Part 2: CPU Alarm + stress exercise

An alarm watches a metric and takes action when it crosses a threshold. This is the **S** in LETS (saturation) in action.

**Console: Create a CPU alarm**
1. **CloudWatch** → **Alarms** → **Create alarm**
2. Select metric → **EC2** → **Per-Instance Metrics** → `CPUUtilization` → select your instance
3. Conditions: **Greater than 60** for **1 out of 1 datapoints** (1-minute period)
4. Name: `high-cpu-demo` → Create alarm

**Exercise: Trigger the alarm**

SSH into your EC2 instance:
```bash
# Spike all CPUs for 5 minutes
stress --cpu $(nproc) --timeout 300
```

In another terminal, watch the app respond while under load:
```bash
watch -n 2 curl -s http://<your-alb-dns>/info
```

What to observe:
- CloudWatch dashboard: `CPUUtilization` climbs toward 100%
- After ~1 minute: alarm flips from `OK` → `IN_ALARM`
- After `stress` exits: CPU drops, alarm returns to `OK`

> 🚨 You just applied the **LETS framework end-to-end**: measured Utilization, watched it hit Saturation, got alerted, and saw it recover.

# Prometheus

You can get LETS signals from any type of data
- Error rates from logs: if too many log level errors (ie. logging.error()) in your applications
- Latency from ALB access logs: ALB access logs have a target_processing_time field on every request.

But its much cheaper to process these with metrics:
Your app already exports metrics at `GET /metrics`. Try it:
```bash

./assets/hit_demo_app.sh <your-alb-dns>

# curl http://<your-alb-dns>/metrics
```

You'll see output like:
```
# HELP http_request_duration_seconds Latency of HTTP requests.
http_request_duration_seconds_bucket{path="/slow",le="0.5"} 2
http_request_duration_seconds_bucket{path="/slow",le="1"} 7

# HELP http_requests_total Count of HTTP requests by path and response code.
http_requests_total{code="200",path="/healthz"} 42
http_requests_total{code="500",path="/error"} 10

# HELP http_requests_in_flight Number of requests currently being served.
http_requests_in_flight 1
```

These are the same LETS signals you're measuring in CloudWatch — just in Prometheus format:
- `http_request_duration_seconds` → **L**atency
- `http_requests_total{code="500"}` → **E**rror rate
- `http_requests_total` (all) → **T**raffic
- `http_requests_in_flight` → **S**aturation

**AWS vs open source:**

| Concept | AWS | Open source |
|---------|-----|-------------|
| Metrics store | CloudWatch Metrics | Prometheus |
| Dashboards | CloudWatch Dashboards | Grafana, Kibana |
| Log storage | CloudWatch Logs | Loki, Elasticsearch, OpenSearch |
| Log shipper | CloudWatch Agent | Fluentd, Fluent Bit, Logstash |
| Alerting | CloudWatch Alarms | Alertmanager, Grafana Alerts |
| Traces | AWS X-Ray | Jaeger, Zipkin, Tempo |
