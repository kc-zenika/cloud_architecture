# ASG

We will look at how to manage compute scaling today.

On AWS ec2, this is managed using Auto Scaling Group (ASG).

**Main idea** --- ASG is a continuous control loop.
- constantly compares the actual state of the fleet (instance count, instance health) against the desired state you've configured
- reconciles any difference by launching (scaling up) or terminating (scaling down) instances. 

### Components
- **Launch Template** — defines what an instance looks like when ASG creates one (AMI, instance type, IAM instance profile, user data).
- **Min / max / desired capacity** — desired is the count ASG actively maintains; min/max bound how far scaling policies are allowed to push it.
- **Scaling policies** — rules attached to the group that adjust desired capacity automatically (target tracking, step, scheduled — see below).
- **Health checks** — how the group decides an instance is unhealthy and needs replacing (EC2 status / ELB checks — see below).
- **The group itself** — launches or terminates instances from the Launch Template to keep the actual instance count matching desired capacity as demand changes.

### Scaling policies:
- **Target tracking** — pick a metric (e.g. CPU 50%) and ASG adjusts capacity to hold it there. Simplest, good default.
- **Step scaling** — define thresholds with different scaling amounts (e.g. +1 instance at 60% CPU, +3 at 90%). More control for spiky load.
- **Scheduled scaling** — set capacity ahead of time for known, predictable patterns (e.g. scale up before a 9am traffic spike).
- **Cooldown period** — pause further scaling actions for N seconds after one fires, so the fleet has time to absorb the change before ASG reacts again. Prevents thrashing.
- **Warmup period** — delays when a *new* instance's metrics start counting toward scaling decisions, since a freshly booted instance often shows a CPU spike while `user_data.sh` runs.
- **Connection draining / deregistration delay** — when an instance is being removed, the ALB stops routing *new* requests to it but lets in-flight ones finish (up to the configured delay) before termination. Avoids cutting off users mid-request.

### Self-healing (unhealthy instance handling):
- ASG health checks come from two sources: **EC2 status checks** (is the instance itself running) and **ELB health checks** (is the app behind it responding, via the ALB target group).
- If a health check fails past its threshold, ASG terminates that instance and launches a replacement to restore desired capacity — no human intervention needed.
