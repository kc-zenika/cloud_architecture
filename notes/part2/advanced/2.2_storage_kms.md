# KMS (Key Management Service)

AWS managed service for creating and controlling cryptographic keys. 
KMS never exposes raw key material — all encrypt/decrypt operations happen inside KMS, so your app never handles the actual key bytes.

## When to use KMS
- **Encrypting AWS services at rest** — KMS integrates natively with most AWS services: EBS volumes (EC2/ASG), RDS databases, S3 buckets, Secrets Manager, and more. You point the service at a CMK and it handles encrypt/decrypt transparently
- **Audit trail requirements** — CloudTrail logs every KMS API call: who decrypted what, and when. Essential for compliance
- **Revoke access without deleting data** — disable a key and no one can decrypt, even if they have the ciphertext. Re-enable to restore access
- **Fine-grained decrypt permissions** — key policy lets you grant different IAM roles different levels of access to the same key, separate from their general IAM permissions

## Key types

|                      | AWS-managed keys     | Customer-managed keys (CMK) |
|----------------------|----------------------|-----------------------------|
| Cost                 | Free                 | $1/month per key            |
| Key policy control   | No (AWS controls it) | Yes                         |
| Cross-account access | No                   | Yes                         |
| Auto rotation        | Every 3 years        | Annual (configurable)       |

**Rule of thumb**: use CMK for anything you care about controlling. AWS-managed keys are fine when you just want encryption without any access policy requirements.

## Best practices
- **Use CMK over AWS-managed keys** — you can't customize the key policy on AWS-managed keys, which blocks you from cross-account access and fine-grained control
- **Enable automatic key rotation** — annual rotation, costs nothing extra for CMK
- **Use key aliases** (`alias/myapp-prod-ebs`) not raw key IDs — key IDs are GUIDs, aliases are human-readable and stable references in Terraform/code
- **Key policy is the primary access control** — IAM alone is not enough. Both the key policy AND IAM must allow access. This is different from most AWS services
- **One key per environment** — dev/staging/prod get separate keys; limits blast radius if a key is misused
- **Never delete keys immediately** — use scheduled deletion (7–30 day window) and disable the key first to verify nothing breaks before committing to deletion
- **Enable CloudTrail** — KMS + CloudTrail gives you a full audit log of every encrypt/decrypt call

## EBS encryption with KMS
1. Create a CMK dedicated to EBS
2. Enable "EBS encryption by default" at the AWS account level → all new EBS volumes use this CMK automatically
3. ASG launches an instance → EBS encrypted transparently, no change to launch template

**IAM grants needed (two separate things):**
- EC2 service principal (`ec2.amazonaws.com`) needs `kms:CreateGrant` on the key — required for EC2 to create the encrypted volume at launch time
- The EC2 instance IAM role needs `kms:Decrypt` + `kms:GenerateDataKey` — required at runtime to read/write the volume
