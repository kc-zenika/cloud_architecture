# What are terraform modules

A module is just a directory of `.tf` files.
A `module` block lets you call *another* directory (local path, git repo, registry) as a reusable, parameterized unit, the same way a function call lets you reuse a block of code instead of copy-pasting it.

### Why

- **Encapsulation** — the caller only ever sees inputs and outputs. You can change how the module builds its resources internally without breaking anyone calling it, as long as the interface (inputs/outputs) stays stable.
- **Reusability** — call the same module multiple times (once per environment, once per app) with different input values instead of duplicating the resource blocks.

### Some Conventions that you might see

- **Inputs** (normally in `variables.tf`) — the contract a caller must satisfy to use the module. Some required, some with defaults.
  - **Variable validation blocks** — a `validation { condition = ... }` inside a `variable` catches bad input at `plan` time instead of failing against the provider's API later. Can reference other variables in the same module (e.g. checking `max_size >= min_size`).
  - **`sensitive = true`** on any variable/output that could leak a secret.
- **Outputs** (normally in `outputs.tf`) — values (ids, ARNs, names) the module exposes so other parts of the config can reference them without reaching into the module's internals.
- provider versions (normally in **`versions.tf`**) — a `terraform { required_providers {...} }` block declaring which provider(s) the module needs.
  - Kept looser than the root's pin (e.g. `>= 6.0` vs. the root's exact `6.38`), since a module shouldn't over-constrain what provider version its caller uses.
- **No `provider` blocks in child modules** — a reusable module always inherits its provider configuration (region, credentials, aliases) from whoever calls it, so the same module can be called from different accounts/regions unchanged.
- **`locals.tf` / `data.tf`** — once a module grows, local values and data sources are sometimes split into their own files purely for readability. Not needed while a module stays small.
- **`README.md`** — purpose, an example call, and an inputs/outputs table, often generated with `terraform-docs`.
- **Pinned `source`/`version`** when a module comes from a registry or git repo (e.g. `source = "git::...?ref=v1.2.0"`) — not relevant to a local path, which always tracks whatever's on disk.

## Segregating into environments (dev/prod)

### Pattern 1: directory per environment

Each environment is a fully separate root module — its own state file (own `backend "s3" { key = ... }`), its own `provider "aws"` block (can even target a different AWS account) — calling the *same* shared modules. Differing values live in a `terraform.tfvars` per environment directory rather than hardcoded into `compute.tf`; Terraform auto-loads a file with that exact name (or `*.auto.tfvars`) from whichever directory it's run in, no `-var-file` flag needed. That keeps `compute.tf`/`variables.tf` byte-identical across environments, so the *only* thing that differs is the tfvars file.

```
aws/
  development/
    provider.tf          # own backend key/bucket, maybe own AWS account
    vpc.tf               # calls modules/vpc (or stays inline, if not extracted)
    variables.tf         # declares min_size/max_size/instance_type/tags/... -- identical to production's
    compute.tf           # calls modules/asg -- identical to production's
    terraform.tfvars     # dev-sized values, auto-loaded by plan/apply
  production/
    provider.tf          # different backend key
    vpc.tf
    variables.tf         # identical to development's
    compute.tf           # identical to development's
    terraform.tfvars     # prod-sized values, auto-loaded by plan/apply

modules/
  asg/
  vpc/            # (future) same extraction pattern applied to vpc.tf
  alb/
```

```hcl
# aws/development/variables.tf and aws/production/variables.tf -- identical
variable "min_size"         { type = number }
variable "max_size"         { type = number }
variable "desired_capacity" { type = number }
variable "instance_type"    { type = string }
variable "tags"             { type = map(string) }
```
```hcl
# aws/development/compute.tf and aws/production/compute.tf -- identical
module "asg" {
  source = "../../modules/asg"
  name   = "part2-app"
  tags   = var.tags

  min_size         = var.min_size
  max_size         = var.max_size
  desired_capacity = var.desired_capacity
  instance_type    = var.instance_type
  # ...
}
```
```hcl
# aws/development/terraform.tfvars
min_size         = 1
max_size         = 2
desired_capacity = 1
instance_type    = "t3.micro"
tags             = { Environment = "dev" }
```
```hcl
# aws/production/terraform.tfvars
min_size         = 2
max_size         = 6
desired_capacity = 3
instance_type    = "t3.small"
tags             = { Environment = "prod" }
```

**Pros:** fully isolated state per environment; can target different AWS accounts; no conditional-logic sprawl; a plain `diff` between `aws/development/terraform.tfvars` and `aws/production/terraform.tfvars` shows exactly what's different.
**Cons:** duplicated boilerplate — `compute.tf`/`variables.tf` are meant to be identical across environments, but they're still two physical copies, and nothing stops one from drifting from the other except discipline (or a tool like Terragrunt, built specifically to keep this pattern DRY).

For a stack this size, this is the better trade-off — which is why the folder sketch reflects it rather than workspaces.

### Pattern 2: single shared root + var-file

One copy of `.tf` files, no `aws/development`/`aws/production` directories at all. Environment is selected at the CLI by pairing a `-var-file` (for values) with a `-backend-config` (for state isolation — a var-file alone does *not* separate state, so this still needs a backend config per environment or you'd apply against the wrong state):

```
part2/
  variables.tf
  compute.tf              # module "asg" { ... using var.* ... }
  backend-dev.hcl          # key = "dev/terraform.tfstate"
  backend-prod.hcl         # key = "prod/terraform.tfstate"
  environments/
    dev.tfvars
    prod.tfvars
```
```bash
terraform init -backend-config=backend-dev.hcl -reconfigure
terraform apply -var-file=environments/dev.tfvars

# ...switching environments...
terraform init -backend-config=backend-prod.hcl -reconfigure
terraform apply -var-file=environments/prod.tfvars
```

**Pros:** lightest-weight of the three — exactly one copy of every `.tf` file, so zero drift risk.
**Cons:** gives up the directory-level guardrail; forgetting to re-`init` with the right `-backend-config` before switching environments means you could apply prod's values against dev's (still-loaded) state — the safety has to come from disciplined scripting/CI, not the file layout itself. Reasonable for a small, single-account stack; less so here since separate AWS accounts per environment is the whole point.

---

Common tags follow the same pattern already used in `vpc.tf` (`local.common_tags = { Environment = "dev" }`) — under pattern 2 that becomes each environment's own `tags` value in its `terraform.tfvars`, merged onto every resource/module call the same way `vpc.tf` already does with `merge(local.common_tags, { Name = ... })`.

# Refactoring the ASG into a module


1. **Find the module boundary.** 
*what changes together vs. independently?*

Here, launch template + ASG + its scaling policy form one module ("the compute layer"); the security group, IAM role, and target group stay in the root because they're shared with other things (the ALB, other IAM attachments).

We can combine the resources in our `asg.tf` and `launch-template.tf` as a module.

2. **Create the modules directory** 

In the repo root, create a `modules/asg` directory in repo's root, and create these 4 files.
- `main.tf`
- `variables.tf`
- `outputs.tf`
- `versions.tf`

Copy the resources content from `asg.tf` and `launch-template.tf` into `main.tf` unchanged first.

For `versions.tf`, add the following, loosen version requirements. 
```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = ">= 6.0"
    }
  }
}
```

3. **Replace root-specific values with `var.*` references.**

Anything that would differ if you called this module a second time (a different app, a different environment) becomes an input.

Basically - what do you think should be parameterized here.
Create variables in `variables.tf` and use var.* in main.tf

Some good candidates:  `name`, `instance_type`, `iam_instance_profile_name`, `security_group_ids`, `subnet_ids`, `target_group_arns`, sizing (`min_size`/`max_size`/`desired_capacity`), `tags`.

4. **Watch for paths that reach outside the module.**

The original `launch-template.tf` did:
```hcl
user_data = base64encode(templatefile("${path.module}/../../assets/user_data.template", { ... }))
```
`path.module` is *relative to the calling module's own directory* — a module that climbs out of itself with `../..` only works by coincidence of where it happens to sit relative to the caller. It'd break if this same module were called from `aws/production/` one directory level deeper, or published and used from another repo entirely. 

The fix: the module takes a plain `user_data` string input; the **caller** (which already knows the repo layout) renders the template and passes the finished, base64-encoded result in. This is the encapsulation principle from above in practice — the module shouldn't need to know where it's being called from.

5. **Declare outputs** 

Outputs are only for what your other resources may need (Think encapsulation).

ie. We can expose `asg_name`, `asg_arn`, `launch_template_id` — even if nothing consumes them yet, this is the seam that lets future code reference the ASG without reaching into the module's internal resource addresses.

6. **Wire it up from the root**

Create a `compute.tf` and use the module like this.
```hcl
module "asg" {
  source = "../../modules/asg"

  name                      = "part2-app"
  iam_instance_profile_name = aws_iam_instance_profile.app_instance_profile.name
  security_group_ids        = [aws_security_group.app.id]
  subnet_ids                = [for s in aws_subnet.private : s.id]
  target_group_arns         = [aws_lb_target_group.app_tg.arn]

  user_data = base64encode(templatefile("${path.module}/../../assets/user_data.template", {
    bucket_name = "workshop-part2-app-${local.account_id}"
  }))

  min_size         = 2
  max_size         = 4
  desired_capacity = 2
}
```

7. **Retire the old resources — and mind the state.** 

You can now comment out the resources in `asg.tf` and `launch-template.tf`.

Try to terraform plan now. what do you see?
```bash
Plan: 3 to add, 0 to change, 3 to destroy.
```

Terraform doesnt know you are doing a refactoring here, it assumes that you are destroying the asg and launch templates. 

The fix in a live stack is a `moved` block. Add the following in `compute.tf`:
```hcl
moved {
  from = aws_launch_template.app
  to   = module.asg.aws_launch_template.app
}

moved {
  from = aws_autoscaling_group.app
  to   = module.asg.aws_autoscaling_group.app
}

moved {
  from = aws_autoscaling_policy.cpu_target_tracking
  to   = module.asg.aws_autoscaling_policy.cpu_target_tracking
}
```

```bash
terraform plan
# Plan: 0 to add, 0 to change, 0 to destroy.

terraform apply 
# should show Apply completed! with no changes
# this is pretty much applying the move

```
Once done we can remove those moved blocks too.

p.s. We could do `terraform state mv` as well, but move is more declarative, especially if you are maintaining a shareable module.
