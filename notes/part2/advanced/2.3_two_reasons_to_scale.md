
# Two Reasons to Scale

## 1. High Availability (HA) — survive failures
Goal: keep the system running when something breaks, not just when traffic is high.

- **Multi-AZ**: spread instances across ≥2 AZs so one AZ failure doesn't take down the app
- min capacity = number of AZs (e.g. min=2 for 2 AZs), desired = same, max = same
- ASG with ALB handles failover automatically — unhealthy instances are replaced, traffic re-routed
- this is about *redundancy*, not *capacity* — you'd run this config even at zero load

Example: prod app at low traffic still runs 2 instances (one per AZ). If AZ-a goes down, AZ-b instance keeps serving. ASG self-heals by launching a replacement in AZ-b or another AZ.

## 2. Performance Scaling — handle load
Goal: add capacity when traffic increases, remove it when traffic drops.

- min = floor (keep lights on), desired = current target, max = ceiling (cost guard)
- scaling policies drive desired up/down based on metrics (CPU, request count, custom)
- over-provisioning wastes money; under-provisioning causes latency spikes or 5xx errors

Example: e-commerce app idles at 2 instances. Black Friday traffic → CPU spikes → ASG scales out to 10. Traffic drops → scales back to 2.

### Key difference
| | HA Scaling | Performance Scaling |
|---|---|---|
| Trigger | AZ/instance failure | Load metric threshold |
| Goal | Survive outages | Handle traffic |
| Min instances | Must stay ≥ AZ count | Can be 1 (cost-optimised) |
| Config focus | Multi-AZ spread | Scaling policies & thresholds |

Both are usually combined in prod: multi-AZ for HA + auto-scaling policies for performance.
