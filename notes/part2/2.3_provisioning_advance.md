# ASG

We will look at how to manage compute scaling today.

On AWS ec2, this is managed using Auto Scaling Group (ASG).

**Main idea** --- ASG is a continuous control loop.
- constantly compares the actual state of the fleet (instance count, instance health) against the desired state you've configured
- reconciles any difference by launching (scaling up) or terminating (scaling down) instances. 

### Components
- **Launch Template** — defines what an instance looks like when ASG creates one (AMI, instance type, IAM instance profile, user data).
- **Min / max / desired capacity** — desired is the count ASG actively maintains; min/max bound how far scaling policies are allowed to push it.
- **Scaling policies** — rules attached to the group that adjust desired capacity automatically (target tracking, step, scheduled — see below).
- **Health checks** — how the group decides an instance is unhealthy and needs replacing (EC2 status / ELB checks — see below).
- **The group itself** — launches or terminates instances from the Launch Template to keep the actual instance count matching desired capacity as demand changes.

### Scaling policies:
- **Target tracking** — pick a metric (e.g. CPU 50%) and ASG adjusts capacity to hold it there. Simplest, good default.
- **Step scaling** — define thresholds with different scaling amounts (e.g. +1 instance at 60% CPU, +3 at 90%). More control for spiky load.
- **Scheduled scaling** — set capacity ahead of time for known, predictable patterns (e.g. scale up before a 9am traffic spike).
- **Cooldown period** — pause further scaling actions for N seconds after one fires, so the fleet has time to absorb the change before ASG reacts again. Prevents thrashing.
- **Warmup period** — delays when a *new* instance's metrics start counting toward scaling decisions, since a freshly booted instance often shows a CPU spike while `user_data.sh` runs.
- **Connection draining / deregistration delay** — when an instance is being removed, the ALB stops routing *new* requests to it but lets in-flight ones finish (up to the configured delay) before termination. Avoids cutting off users mid-request.

### Self-healing (unhealthy instance handling):
- ASG health checks come from two sources: **EC2 status checks** (is the instance itself running) and **ELB health checks** (is the app behind it responding, via the ALB target group).
- If a health check fails past its threshold, ASG terminates that instance and launches a replacement to restore desired capacity — no human intervention needed.

## Create ASG
Goal: define the ASG and its scaling policy in `aws/development/asg.tf`. 

- search for [`aws_autoscaling_group`](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/autoscaling_group) and read the Basic Usage example
- you'll need:

  | Field | Value |
  |-------|-------|
  | `name` | `part2-app-asg` |
  | `min_size` / `max_size` / `desired_capacity` | 2 / 4 / 2 |
  | `vpc_zone_identifier` | the **private** subnets (`[for s in aws_subnet.private : s.id]`) |
  | `health_check_type` | `"EC2"` (the default — we'll switch this once there's a target group to check against) |
  | `health_check_grace_period` | `60` |
  | `launch_template` block | `id = aws_launch_template.app.id`, `version = "$Latest"` |
  | `tag` block | `key=Name, value=part2-app-asg`, `propagate_at_launch = true` |

  - _`health_check_type=EC2` first so we can deploy this as a standalone ASG without load balancer. Uses AWS managed system/instance checks._
  - `propagate_at_launch = true` _adds Name tag to all the instances launched by this ASG._

- search for [`aws_autoscaling_policy`](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/autoscaling_policy) — you'll need:

  | Field | Value |
  |-------|-------|
  | `name` | `part2-app-cpu-target-tracking` |
  | `autoscaling_group_name` | `aws_autoscaling_group.app.name` |
  | `policy_type` | `"TargetTrackingScaling"` |
  | `target_tracking_configuration` → `predefined_metric_specification` → `predefined_metric_type` | `"ASGAverageCPUUtilization"` |
  | `target_tracking_configuration` → `target_value` | `50` |

  - see `ASGAverageCPUUtilization` predifined metric type
    - AWS manages the underlying CloudWatch alarms and step-adjustment math for you — you just supply the metric and a `target_value`, and it works out how many instances to add or remove to converge on it (the same continuous-loop idea from "Main idea" at the top, just automated per-metric)
  - using `target_value = 50` so the demo we will try out later works easier

    | Reference point | Approx CPU | Why it matters |
    |------------------|-----------|-----------------|
    | Idle / ordinary traffic on `t3.micro` | ~10% | Comfortably below 50%, so normal traffic never triggers a false scale-out |
    | `stress-ng --cpu 2` | ~100% | Immediately blows past 50%, so the ASG scales out clearly and quickly |

```bash
terraform plan
terraform apply
```
- AWS Console → EC2 → Instances, filter by the `Name` tag you used — 2 instances should launch into the private subnets

## Create and point ALB to ASG
Goal: build the ALB path (security group → ALB → target group → listener) in `alb.tf`, then wire the ASG into it.

### 1. ALB security group
- search [`aws_security_group`](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/security_group): `name = "part2-alb"`, same `vpc_id` pattern as `aws_security_group.app`
- search [`aws_vpc_security_group_ingress_rule`](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/vpc_security_group_ingress_rule) / [`_egress_rule`](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/vpc_security_group_egress_rule) again — same pattern as part 1's security groups section

  | Rule | Direction | Port | Source / Dest |
  |------|-----------|------|----------------|
  | `alb_in_http` | Ingress | 80 | `0.0.0.0/0` |
  | `alb_out_app` | Egress | 8080 | `referenced_security_group_id` → `aws_security_group.app.id` |

- now that `aws_security_group.alb` exists, go back to `ec2-security-group.tf` and **uncomment `app_in_http` and `app_out_https`** — they referenced an ALB security group that didn't exist yet, which is why they were commented out

### 2. The ALB resource
- search [`aws_lb`](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/lb) — you'll need:

  | Field | Value |
  |-------|-------|
  | `name` | `part2-app-alb` |
  | `internal` | `false` (internet-facing) |
  | `load_balancer_type` | `"application"` |
  | `security_groups` | `[aws_security_group.alb.id]` |
  | `subnets` | the **public** subnets (`[for s in aws_subnet.public : s.id]`) |

### 3. Target group (ALB's backend)
- search [`aws_lb_target_group`](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/lb_target_group) — you'll need:

  | Field | Value |
  |-------|-------|
  | `name` | `part2-app-tg` |
  | `port` | `80` |
  | `protocol` | `"HTTP"` |
  | `vpc_id` | `aws_vpc.main.id` |

  - `health_check` block
  ```hcl
  health_check {
    path                = "/healthz"
    protocol            = "HTTP"
    matcher             = "200"
    interval            = 30
    timeout             = 5
    healthy_threshold   = 2
    unhealthy_threshold = 2
  }
  ```
  - pick `interval`, `timeout`, `healthy_threshold`, `unhealthy_threshold` yourself — there's no single right answer, but weigh: how fast do you want a bad instance pulled from rotation vs. how many false positives (e.g. a slow GC pause) you're willing to tolerate?

### 4. Listener (Entry points for ALB)
- search [`aws_lb_listener`](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/lb_listener) — you'll need:

  | Field | Value |
  |-------|-------|
  | `load_balancer_arn` | `aws_lb.app_alb.arn` |
  | `port` | `"80"` |
  | `protocol` | `"HTTP"` |
  | `default_action` → `type` | `"forward"` |
  | `default_action` → `target_group_arn` | `aws_lb_target_group.app_tg.arn` |

### 5. Point ASG as Targets of ALB
- back in `asg.tf`, add `target_group_arns = [aws_lb_target_group.app_tg.arn]` to `aws_autoscaling_group.app` — this is the step this whole section is named after
- also flip `health_check_type` from `"EC2"` to `"ELB"` now that there's actually something for it to check — this is what makes the ASG replace an instance that's up but failing `/healthz`, not just one that's outright down
- once both are set, the ASG registers/deregisters its instances against this target group automatically as it launches/terminates them — no manual attachment step needed

### 6. Apply and verify
```bash

terraform apply
```
- AWS Console → EC2 → Target Groups → your target group → **Targets** tab — watch instances go from `initial` → `healthy`
- grab the ALB's DNS name (Console → EC2 → Load Balancers) and hit it:
```bash

curl http://<alb-dns-name>/info
```

## Playing with our ASG
Before starting, grab two things you'll reuse across all 3 demos:
- ALB DNS name — Console → EC2 → Load Balancers → `part2-app-alb`
- The 2 running instance IDs — Console → EC2 → Auto Scaling Groups → `part2-app-asg` → **Instance management** tab

Keep a terminal open hitting `/info` throughout — it shows which instance answers, so you can watch instances come and go live:
```bash
watch -n2 curl -s http://<alb-dns-name>/info
```

### Demo 1 — terminate one instance manually → watch self-healing
Goal: show that ASG reconciles actual vs desired count, no matter *why* an instance disappeared.

1. Console → EC2 → Instances → pick one of the two `part2-app` instances → **Instance state → Terminate instance**
   - or CLI: `aws ec2 terminate-instances --instance-ids <instance-id>`
2. Console → EC2 → Auto Scaling Groups → `part2-app-asg` → **Activity** tab
   - you'll see the terminate wasn't logged as an ASG action, but a *new* "Launching a new EC2 instance" activity appears almost immediately after — ASG noticed actual count (1) < desired (2) and reconciled
3. Console → target group `part2-app-tg` → **Targets** tab — watch the old target disappear and a new one go `initial` → `healthy`
4. Your `/info` loop should show the hostname change once the new instance passes its health check

_Ask yourself: would this still work if `desired_capacity` had been 1? (No — ASG only replaces to restore desired count, terminating a healthy fleet at desired capacity does nothing.)_

### Demo 2 — stress a node's CPU → watch it scale out
Goal: trigger the target-tracking policy (`ASGAverageCPUUtilization`, target `50`) instead of the health-check path.

1. Connect to one instance: Console → EC2 → Instances → select instance → **Connect** → Session Manager
2. Baseline check: `curl localhost:8080/info` — `load1` should be low (~0.0-0.2 on an idle `t3.micro`)
3. Spike CPU using the `stress-ng` binary already installed by `user_data` (t3.micro = 2 vCPUs):
  ```bash
  stress-ng --cpu 2 --timeout 300s --temp-path=/tmp
  ```
4. Console → Auto Scaling Groups → `part2-app-asg` → **Monitoring** tab — watch `CPUUtilization` climb past the `50` target
   - this takes a few minutes, not seconds — CloudWatch metric granularity + alarm evaluation periods aren't instant, unlike Demo 1's near-immediate reconciliation
5. Once the alarm fires, **Activity** tab shows a scale-out launched by the policy (not a health check) and **Instance management** shows desired capacity rise (2 → 3/4)
6. Let the 300s timeout expire (or `pkill stress-ng`) and wait — CPU drops back under 50%, and ASG eventually scales desired capacity back down to 2, terminating the extra instance(s)

_Ask yourself: why `--cpu 2` and not `--cpu 1`? (Matches the t3.micro's 2 vCPUs — 1 worker would only load one core, and the average utilization metric might not clear 50%.)_

### Demo 3 — stop the app (not the instance) → ELB marks it unhealthy → ASG replaces it
Goal: show why `health_check_type = "ELB"` matters over `"EC2"` — this catches "instance up, app down," which a pure EC2 status check would miss.

1. Connect via Session Manager to one instance (as in Demo 2)
2. Confirm it's serving traffic: `curl localhost:8080/healthz` → `ok`, `systemctl status app.service` → `active (running)`
3. Stop just the app, leave the instance running: `sudo systemctl stop app.service`
4. `curl localhost:8080/healthz` now fails (connection refused) from inside the instance itself
5. Console → target group `part2-app-tg` → **Targets** — this target flips `healthy` → `unhealthy` after `unhealthy_threshold=2` failed checks at `interval=30s` (~60-90s including the request timeout)
6. Console → Auto Scaling Groups → `part2-app-asg` → **Activity** tab — once ASG (trusting the ELB verdict, since `health_check_type = "ELB"`) sees the unhealthy target, it terminates that instance and launches a replacement — same reconciliation loop as Demo 1, just triggered by the target group instead of a manual termination
7. Watch the replacement register and pass health checks in the target group, and your `/info` loop pick up the new hostname

_Ask yourself: if `health_check_type` were still `"EC2"` here, would ASG have noticed anything wrong? (No — the instance and OS are fine; only the app process died. EC2 status checks operate at the hypervisor/OS level and can't see that.)_
